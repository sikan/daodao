DAODAO CODEX CHECKLIST

日记待提交改动审查规范
版本：2026-11-08

用途

本规范用于审查本仓库相对当前 HEAD 的全部待提交改动。

主要正文：daodao.master.txt
脱敏规则：redactions.json
字体更新说明：FONT_SUBSET_UPDATE.md
字体已知限制：FONT_KNOWN_LIMITATIONS.md
字体来源说明：assets/fonts/README.md

除非作者明确要求重建字符集或进行其他写入操作，审查必须保持只读：不得修改、格式化、暂存、提交、恢复或删除任何仓库文件。

每次审查都必须重新读取当前磁盘中的文件、重新确认 HEAD，并重新检查全部待提交改动。不得只检查最后增加的几行，也不得直接沿用上一次的检查结果。


一、审查目标与基本原则

1. 首要目标

防止以下问题进入提交：

• 原有实质内容被误删；
• 原文被无意改写；
• 增加空行、段落或新日记时误触旧文字；
• 批量替换、输入法选字或复制粘贴造成隐蔽损坏；
• 新增或修改内容中出现明确的文字、事实、脱敏、隐私、格式或技术错误；
• 正文已经变化，但字体字符集、缓存引用或生成结果没有同步；
• 待提交文件之外还存在未被检查的暂存、未暂存或未跟踪内容。

2. 只读边界

普通审核中：

• 不修改文件；
• 不运行会自动格式化、修复或更新仓库文件的命令；
• 不暂存、不提交；
• 不使用 git restore、git checkout 等改变工作区的命令；
• 不把站点预览或其他生成内容写入仓库；
• 如需生成站点或脱敏预览，只能输出到仓库外的专用临时目录。

如果作者明确要求“重建字符集”“构建字符集”或“直接操作”，可以执行字体生成；但生成结束后必须重新审查全部待提交改动，包括新产生的二进制字体和清单文件。

3. 以磁盘为准

审查结论只适用于当前磁盘中已经保存的版本，不适用于编辑器中尚未保存的缓冲区。

4. 以当前 HEAD 为准

每轮都必须重新确认当前 HEAD。作者可能已经提交上一批内容，不能假设本轮 HEAD 与上一轮相同。

5. 完整检查

发现一个问题后不得停止。仍需继续检查剩余文字、脱敏规则、字体、日期和全部文件状态，最后一次性报告所有问题。


二、Git 状态与版本完整性

1. 覆盖全部状态

每轮必须查看：

• 未暂存修改；
• 已暂存修改；
• 同一文件中同时存在的已暂存和未暂存修改；
• 新增、删除、重命名和复制的文件；
• 未跟踪文件；
• 文件权限、文件类型、符号链接、子模块或文件名变化；
• 二进制文件变化。

未跟踪文件不会出现在普通的 git diff HEAD 中，必须单独检查。

2. 相对 HEAD 检查完整差异

应明确报告：

• 每个文件增加和删除多少行；
• 哪些是纯新增；
• 哪些是对原有行的替换；
• 是否删除或改变段落、句子、短语、标点、空格或单个字符；
• 是否出现重命名、权限变化或其他非正文属性变化。

必须分别查看：

• 工作区未暂存差异；
• 暂存区差异；
• 相对 HEAD 的合并差异。

3. 不能只根据行数判断误删

daodao.master.txt 的一个段落通常占一整行。只改变一个字符，也可能显示为“一行删除、一行新增”。

因此必须：

• 对所有旧行替换进行逐词或逐字符比较；
• 必要时使用 word diff 或字符级 diff；
• 区分真正删除与整行因一个字符变化而被 Git 视为替换；
• 检查长段落是否被截断、拼接、重复或整体替换；
• 检查批量替换是否污染无关位置。

曾出现过把原文中的单个字母 s 批量误替换为某个小朋友姓名的情况，因此不能只肉眼浏览新增行。

4. 最终必须分别回答

• 有没有删除原有实质内容？
• 有没有无意改变原意？
• 有没有只改变标点或空格，却破坏句子结构？
• 除作者明确进行的局部改写外，旧文章是否完整保留？

即使没有删除实质文字，只要旧标点、引号、空格或单个字符被改坏，也必须单独报告，不能笼统地说“没有误删”。

5. 建议执行或等价完成的 Git 检查

git rev-parse HEAD
git status --short
git diff HEAD --stat
git diff HEAD --numstat
git diff HEAD --name-status
git diff HEAD --summary
git diff HEAD --check
git diff HEAD
git diff
git diff --cached
git ls-files --others --exclude-standard

对旧行替换还应使用 word diff 或字符级比较。


三、连续多轮复查与保存状态

1. 每轮都从磁盘重新读取文件，不依赖上一轮保存的 diff 或口头结论。

2. 可以记录 daodao.master.txt 及其他关键文件的 blob 或哈希，用于判断新修改是否真正保存。

3. 如果作者说已经修改，但文件 blob 和完整差异与上一轮完全相同，应明确说明：

• 当前磁盘文件没有变化；
• 修改可能尚未保存；
• 或修改后又被恢复。

4. 如果 blob 已改变，应定位相对上一轮新增的细微变化；但仍必须对相对当前 HEAD 的全部待提交改动做完整检查。

5. “可以提交”的结论只适用于最终检查时已经保存的磁盘版本。如怀疑编辑器仍有未保存内容，必须注明。


四、问题等级与判断门槛

1. 明确错误：必须修正

包括但不限于：

• 确定的错别字、漏字、重复字或输入法选字错误；
• 引号、括号或书名号缺失、方向错误或嵌套错误；
• 旧内容被意外删除或替换；
• 句子缺少必要成分，无法形成合理语法关系；
• 存在多个明显不同的解释，且无法从上下文确定原意；
• 时间、数字、事实或上下文明显矛盾；
• 数学乘法使用字母 x、X、ｘ或Ｘ代替乘号 ×；
• 文件格式、JSON、脱敏规则、字符集或生成文件确定有误。

2. 疑似问题：需要作者确认

包括但不限于：

• 很像输入错误，但存在合理的有意解释；
• 可能少了一个词，但口语中仍能成立；
• 专有名词或人物原话无法完全核实；
• 指代略有歧义，但读者大体可以判断；
• 信息组合可能造成间接识别；
• 名称变体可能是有意措辞，也可能是误写。

此类问题不能直接宣称为错误，也不能擅自改写。

3. 可选润色：不阻止提交

包括：

• 更正式、更书面或更顺畅的替换；
• 调整语序后读起来更舒服；
• 减少重复的“的”“了”“然后”；
• 把可理解的口语换成书面语；
• 把能够理解的压缩表达展开。

不要把可选润色说成必须修改。若作者要求“除非确定错误，否则不要指出”，则不应继续列出纯润色建议。

4. 判断门槛

一句话虽然不标准、罕见或压缩，但如果存在自然的口语解析且意思可以明确确定，就不应判为语法错误。

只有在下列情况下，才应作为明确问题：

• 找不到合理的语法解析；
• 必须凭空补出关键成分；
• 标点使句意发生错误变化；
• 不同解析会造成明显不同的事实含义；
• 上下文无法消除歧义。


五、新增和修改文字的逐字校对

必须结合 diff 前后的上下文逐字检查所有新增文字和被修改的旧文字，寻找：

1. 错别字、同音字、形近字和输入法错误；
2. 漏字、漏词、多字、重复字和重复短语；
3. 意外敲入、粘贴错位和替换错误；
4. 句子截断或两个句子意外粘连；
5. 主语、谓语、宾语或必要中心词缺失；
6. 词序异常到需要读者猜测；
7. 指代对象不清或中途更换主语；
8. 量词、介词、连词或必要标点遗漏；
9. 修饰语错误附着到另一个名词或动作；
10. 引号、括号和书名号是否成对并正确嵌套；
11. 中文和英文标点是否合理；
12. 英文大小写、单复数、冠词和拼写；
13. 人名、品牌、车型、作品名和术语拼写；
14. 数字、单位和项目名称的表达是否一致；
15. 日期、年龄、年份和事件先后关系是否自洽；
16. 算术、数量级、单位换算和文中应用题是否成立；
17. 乘法是否使用 ×，而不是字母 x 或 X；
18. 同一名称或术语是否发生无意变化；
19. 是否存在乱码、不可见字符或异常替换字符。

不能只看孤立的一句。主语、日期、指代和事件关系可能来自前一段或同一日期的其他段落。


六、尊重私人日记风格与历史记录

1. 不要因为句子不够正式就认定为错误。

2. 不要把全文改写成新闻稿或正式散文。

3. 孩子的直接引语应尽量原样保留，包括：

• 口语停顿；
• 重复；
• 自我修正；
• 不标准语法；
• 错用词语；
• 当时真实说错的数学、科学或事实知识。

4. 爸爸、妈妈或其他人物当时确实说错、算错的内容，也可能是日记需要保留的历史记录。

5. 必须区分：

• 叙述者当前作出的事实陈述；
• 人物当时说的话；
• 日记作者的猜测；
• 玩笑、反讽和夸张；
• 括号中的事后补充或纠正。

6. 人物引语中的错误不应自动判为文章错误。如果正文已经表现出怀疑、纠正或保留态度，通常可以保留。

7. 作者明确表示希望保留的表达，后续不得反复建议修改，除非：

• 该句后来又发生变化；
• 新上下文使其产生新的明确错误；
• 发现此前未注意到的实质性问题。

8. 作者没有采纳某条润色建议，不代表后续应降低检查标准。仍需继续指出新出现的明确错误、漏字和无法理解的表达。


七、已知的作者表达偏好

以下表达或类型曾被作者明确认为可以接受。除非上下文变化或出现确定错误，不应反复建议改写：

• 「爸爸被岛岛直接电话从床上叫起来去送上学」
• 「用铅笔涂涂画画了很多」
• 「一张打印出来的岛岛和妈妈住处的猫猫」
• 特定上下文中的「原因是由于」：前半解释岛岛心急，后半解释爸爸行为，并非简单同义重复
• 「岛岛坚持在人行道还要再里面的位置」
• 「在两次试骑和分析过车型细节之后」
• 「爸爸意思凯迪拉克……」
• 「翻到有一页『What is this number?』给爸爸看」
• beyond wildest dreams 有意不加 my，以避免突出第一人称
• 「把洗了第二次的白色跑步鞋带着给岛岛在上学路上换上」
• 「打了就一段话的草稿」
• 「快一年的小天才手表」
• 「还只是勤俭节约穿太多年了」

这些决定只适用于原有上下文，不是对所有类似结构的永久豁免。


八、中西文、数字、数学符号和空格

1. 中西文之间通常使用一个半角空格

中文与以下内容相邻时通常留一个半角空格：

• 英文单词；
• 英文缩写；
• 阿拉伯数字；
• 型号或数值。

例如：

使用 iPhone
学习 RGB 模式
跑了 50 米
填了 2000 年
可可含量为 85%

2. 英文或型号内部不能机械拆开

例如：

iPhone XS Max
DS Automobiles
Bugatti Bolide
AMC 8
Z12
W16
9/11

3. 乘号固定规则

数学乘法、数量相乘、接力项目和其他表示“乘”的场合，必须使用真正的乘号 ×（U+00D7），不得使用拉丁字母 x 或 X，也不得使用全角字母 ｘ 或 Ｘ。

推荐写法：

4 × 50
6 × 8 = 48
长 3 × 宽 2

错误写法：

4 x 50
4 X 50
4ｘ50
4Ｘ50

乘号两侧通常各留一个半角空格，除非引用的界面原文、正式项目名称或仓库既有特殊格式明确要求其他写法。

每次审查都必须：

• 检查全部新增和修改文字中的 x、X、ｘ、Ｘ；
• 搜索数字或数量表达式附近的字母 x/X，判断它是否被当作乘号；
• 对 daodao.master.txt 做全篇检索，防止批量替换或补写旧日记引入新的错误；
• 区分本轮待提交错误与 HEAD 中原已存在的历史写法；
• 如发现历史写法，应单独标明它不属于本轮差异，不能谎称是本次修改造成的。

以下情况中的 x 或 X 不应机械替换：

• 代数变量 x；
• 型号、品牌、产品名或专有名词中的 X，例如 XBOX、iPhone X、xDrive；
• 英文单词本身包含的 x；
• 人物直接引用的字母名称；
• 界面、文件名、代码、网址或作品原文；
• 有意保留的逐字转录。

是否表示乘法必须结合上下文判断，禁止对全文进行无差别批量替换。

4. 其他特殊规则

• 数字与百分号之间不加空格：85%，不是 85 %；
• 日期标题 YYYYMMDD 内部不加空格；
• 中文全角标点、括号、书名号和引号与相邻文字之间通常不加空格；
• 英文句子内部按英文规则排版；
• 对界面原文、品牌原文和人物直接引语，应优先保留原貌；
• 不要通过批量替换机械添加或删除空格。

5. 异常空白和特殊字符

检查：

• 连续两个空格；
• 行首或行尾空格；
• 制表符；
• 不换行空格；
• 零宽空格；
• Unicode 行分隔符或段落分隔符；
• 全角和半角字符混用；
• 因复制网页文字带入的特殊字符。


九、引号、问号和直接引语标点

1. 完整直接引语通常写作：

爸爸问：「你去吗？」

问号属于引语，放在引号内。

2. 如果引号中的内容只是外层句子的一个成分，外层句号通常放在引号外：

大声拜拜的时候补了一句「饼干记得吃」。

3. 如果引语本身是问句或感叹句，问号或感叹号放在引号内：

岛岛问：「为什么？」

4. 如果外层句子询问某个被引用的陈述，而引文自身不是问句，问号放在引号外：

你说的是「马上回来」吗？

5. 嵌套引用通常使用外层「」、内层『』。

6. 人物停顿、语气中断和自我修正可以使用省略号并保留原貌。正文中的中文省略号通常使用 ……；英文原文或界面文字例外。

7. 不要因为直接引语缺少书面语成分就擅自补词。


十、日期和段落结构

daodao.master.txt 中的日记日期通常是单独一行的八位数字 YYYYMMDD。

每轮检查：

1. 日期是否按时间递增；
2. 是否存在重复日期；
3. 是否严格为八位数字；
4. 日期是否为有效日历日期；
5. 必要时验证对应星期几；
6. 新内容是否位于正确日期下面；
7. “今天”“昨天”“前天”“下个月”等相对时间是否与日期一致；
8. 教师节、比赛日、生日等日期是否存在明显矛盾；
9. 日期标题与前后段落之间是否有正确空行；
10. 正文段落之间是否保持仓库既有格式；
11. 文件末尾是否只有一个换行符，即正文最后一个字符后有一个 \n，但没有额外空白段落；
12. 是否出现异常连续空白行；
13. 是否残留 Git 冲突标记：<<<<<<<、=======、>>>>>>>。

缺少某一天不算错误，当天可能没有日记。

应运行 git diff HEAD --check 或等价检查，确认没有尾随空格和末尾空行问题。


十一、连续编号专题的全量核对

“惊喜礼品”这类跨越多篇日记并具有连续编号的专题记录，每次提交前都必须检查完整历史，不能只检查本次新增或修改的句子。

1. 每轮重新全量检索

检索：

• 惊喜礼品；
• 惊喜礼物；
• 第×弹；
• 第 × 弹；
• 第×波；
• 阿拉伯数字编号；
• 可能由输入、改写或复制产生的近似名称。

即使本轮改动完全没有涉及“惊喜礼品”，也必须重新核对全部记录。

2. 为每条记录确认

• 所属日记日期；
• 当前磁盘文件行号；
• 是否明确写有编号；
• 中文数字或阿拉伯数字对应的实际序号；
• 第一条没有明确写“第一弹”时，能否由后续“第二弹”及上下文确认其为第一条；
• 后续是否严格连续递增；
• 是否存在缺号、跳号、倒序或重复编号；
• 是否在同一天无意写入两个相同编号；
• 是否有同一记录被重复叙述却使用不同编号；
• 补写旧日记后，日期顺序和编号顺序是否仍然一致。

不得把已知最高编号当作永久终点。每轮都必须从当前磁盘正文重新计算。

3. 检查日期与编号关系

把每条记录归入它上方最近的有效日期标题，并确认：

• 日期标题格式正确且日期有效；
• 各条记录按日期顺序出现；
• 编号没有随着日期前进而倒退；
• 同一日期出现多条时，能从上下文判断它们确实是不同记录；
• 插入较早日期的记录后，后续编号是否需要顺延。

4. 检查名称变体

关注：

• “惊喜礼品”误写为“惊喜礼物”；
• “第十九弹”被输入法误写为相近字；
• “第十弹”突然变成“第 10 弹”；
• “第×弹”突然变成“第×波”；
• 原本属于该系列的记录改写后失去统一名称；
• 普通使用“惊喜”或“礼品”的句子被错误计入该系列。

名称变化不一定是明确错误；无法确认作者意图时，应列为需要确认的问题。

5. 修改历史记录后的处理

如果在较早日期插入、删除或改写一条“惊喜礼品”，必须重新核对它之后的全部编号。

如果插入新记录会导致后续编号顺延，必须明确报告；不能允许两个记录共用同一编号，也不能只检查插入句本身。

6. 最终报告要求

每轮都应说明：

• 共检索到多少条相关记录；
• 当前序列从第一条连续到第几弹；
• 日期顺序是否正常；
• 是否存在缺号、跳号、倒序或重复编号；
• 是否存在需要作者确认的名称变体。

检查正常时也应明确写明：

“惊喜礼品”已全量核对，目前从第一条至当前最高编号连续，日期顺序正常，没有缺号、重复编号或意外名称变体。


十二、脱敏与隐私检查

1. 检查新增和修改内容中的身份信息

提取并核对：

• 小朋友真实姓名；
• 英文名；
• 真实昵称或小名；
• 家长姓名；
• 老师、教练姓名；
• 车牌号；
• 门牌号、房号；
• 学校、班级、俱乐部；
• 精确地点；
• 精确日期和时间；
• 比赛名称、项目和成绩；
• 医疗、纪律处分、冲突和负面评价等敏感信息。

2. 核对 redactions.json

对于每个需要脱敏的名字：

• 必须存在精确匹配的 from → to；
• 不能只确认“有一条相似规则”；
• 确认正文实际写法、空格、繁简体和大小写可以匹配；
• 同一个人的中文名、英文名和昵称应分别考虑；
• 区分本轮新增规则、历史已有规则和完全遗漏的规则。

3. redactions.json 结构

确认：

• JSON 可以正常解析；
• version 和 replacements 结构正确；
• 每项都有非空的 from 和 to；
• from 不重复；
• 没有完全相同或互相冲突的规则；
• 较长名字与较短字符串之间不会错误覆盖；
• to 不会再次命中另一条 from 而产生级联替换；
• 拉丁字母姓名的大小写匹配符合实际替换逻辑；
• 替换结果没有残留真实姓名的一部分。

4. 实际替换效果

在仓库外构建脱敏预览，验证：

• 新增真实姓名确实被替换；
• 替换后上下文仍可阅读；
• 没有误伤普通词语；
• 没有因规则顺序发生二次替换；
• 输出中不存在任何 from 原始字符串。

5. 直接标识和间接识别

除姓名外，还要检查信息组合造成的重新识别风险，例如：

• 精确日期＋学校＋班级＋比赛项目；
• 俱乐部＋成绩＋年龄组；
• 公开比赛名称＋具体项目＋公开成绩；
• 小区、门牌、路线和固定时间；
• 罕见事件＋人物关系。

此类信息未必必须删除，但必须作为“隐私风险，需要作者确认”报告，不能擅自改写。

常见昵称、只有姓氏的“某老师／某教练”、家庭称谓和文章主体“岛岛”不必自动认定需要脱敏。公共人物姓名也不需要脱敏。

对未成年人、老师或学校的负面评价和指控，应提醒公开发布风险，但不能擅自删除。


十三、事实与逻辑检查

适度核实：

• 汽车车型、品牌、发动机和产品名称；
• 书名、电影名、歌曲名和播客名；
• 人名及人物经历；
• 科学、数学、计算机和体育术语；
• 比赛项目和规则；
• 历史事件、日期和数字；
• 前后叙事是否自相矛盾。

1. 区分信息来源

• 叙述者明确断言的事实：应更严格核实；
• 孩子或人物的原话：即使事实错误，也可能需要原样保留；
• 已被后文纠正的错误：不应再次把原话判为文章错误；
• 使用“似乎”“好像”“据说”“大概”等表达：属于保留判断，不应改成确定事实；
• 玩笑、类比和夸张：不要按字面事实纠正。

2. 外部查询原则

• 事实较新、容易变化、非常专业或无法可靠回忆时才查询；
• 当前产品、赛事、电影和规则应优先查询；
• 技术事实优先使用厂商、组织机构或其他第一方资料；
• 不为润色进行无关调查；
• 使用网络资料时，最终报告中的事实结论应附准确来源；
• 只能确认节目、嘉宾或事件存在，却无法核对音频逐字内容时，应明确写“无法独立确认逐字转录”。


十四、字体字符集与站点构建检查

字符集检查是每次日记提交前的固定技术门槛，不能只在肉眼发现生僻字时进行。

1. 相关文件

FONT_SUBSET_UPDATE.md
FONT_KNOWN_LIMITATIONS.md
scripts/build-site.mjs
scripts/build-fonts.py
scripts/requirements-fonts.txt
scripts/font-subset-manifest.json
assets/fonts/README.md
.github/workflows/publish.yml

2. 基本原则

• 每次完成正文、脱敏规则或界面文字修改后，都必须运行站点构建检查；
• 不要手工猜测某个汉字是否已经包含在字体中；
• 构建成功时，不应为了保险而无意义地重建字体；
• 只有构建明确报告字体子集过期时，才需要重建；
• 字体重建应放在本轮文字修改完成之后；
• 重建后如果再次修改正文、脱敏规则或界面文字，必须重新运行构建检查；
• 对 Emoji、罕见拉丁字母、特殊数学符号和 CJK 范围外字符，还需另外检查实际字体覆盖与浏览器回退；
• 每次涉及字体变化时都应读取 FONT_KNOWN_LIMITATIONS.md，确认没有新增或扩大已知限制。

3. 普通审核保持只读

普通日记审核可以将站点构建到仓库外的专用临时目录，例如：

FONT_CHECK="$(mktemp -d /tmp/daodao-font-check.XXXXXX)"

node scripts/build-site.mjs --mode redacted --output "$FONT_CHECK/redacted"
node scripts/build-site.mjs --mode raw --output "$FONT_CHECK/raw"

不得把输出写入不明确的目录、仓库根目录或包含其他重要数据的目录。构建脚本会清理指定输出目录，因此必须使用专用临时目录。

4. Node.js 环境

当前 GitHub Actions 发布流程使用 Node.js 24。本地检查应优先使用 Node.js 24，以尽量与发布环境一致。

运行前可以执行：

node --version

如果 node 不在 PATH 中，可以使用本机已经确认可用的 Node.js 24 可执行文件，但不要把某台机器专用的绝对路径写入跨机器通用规范，也不得因此省略构建。

5. 判断是否需要重建

如果 redacted 和 raw 两种模式均成功构建，且没有字体清单、字体哈希、缓存引用或缺失码位错误，说明当前脚本覆盖范围内的 CJK 字符集完整，不需要重建。

如果出现类似错误：

The reading-font subset is stale (U+....). Run scripts/build-fonts.py before publishing.

必须记录：

• 缺失码位的 Unicode 编号；
• 码位对应的实际字符；
• 字符来自哪个文件和哪一行；
• 它是正文字符、脱敏替换字符、界面字符还是意外字符；
• 是否可能由复制粘贴、异体字、繁简体差异或不可见字符引入。

如果字符本身是错误输入，应先修正文字，而不是把错误字符加入字体。

6. 自动字符收集范围

当前字体脚本从以下文件收集 CJK 字符：

daodao.master.txt
redactions.json
index.html
app.js
typography.js

脚本还会加入一组基础中文标点。

因此，新增日记、脱敏替换目标、界面文字、中文全角符号、CJK 扩展字符、兼容字符和脚本覆盖范围内的日文假名都可能触发字符集更新。

自动 stale-subset 检查只覆盖 build-site.mjs 和 build-fonts.py 定义的 CJK 范围及相关标点，不等于验证全部 Unicode 字符。

Daodao Garamond 的拉丁字符并不是按日记实际使用字符逐个收集，而是保留脚本定义的固定拉丁字符范围。

7. 审核与重建权限边界

如果作者只要求审核：

• 只能运行只读检查和仓库外构建；
• 如发现字符集过期，应报告需要重建；
• 在重建完成前不能给出“可以提交”的结论；
• 不得擅自运行会更新仓库文件的 scripts/build-fonts.py。

如果作者明确要求重建：

• 可以运行字体生成脚本；
• 重建完成后必须重新检查全部待提交改动；
• 生成文件必须和正文一起纳入相对当前 HEAD 的审核。

8. Python 工具环境

字体生成工具必须安装在仓库外的隔离虚拟环境中，例如：

FONT_WORK="$(mktemp -d /tmp/daodao-font-work.XXXXXX)"
python3 -m venv "$FONT_WORK/venv"
"$FONT_WORK/venv/bin/python" -m pip install -r scripts/requirements-fonts.txt

当前固定依赖以 scripts/requirements-fonts.txt 为准；制定本版规范时为：

fonttools[woff]==4.67.0

如果默认 Python 无法创建环境或安装固定依赖，应改用兼容的 Python 3 解释器。

不得为了绕过环境问题而：

• 随意降低或升级 FontTools；
• 修改生成脚本的校验逻辑；
• 使用来源不明的全局 Python 包；
• 关闭上游字体哈希检查；
• 跳过最终双模式构建。

Python 解释器的版本或路径本身不会降低生成质量。只要固定依赖安装成功、固定字体来源通过哈希检查、生成脚本成功并通过全部后续验证，最终成果就是完整有效的。

9. 上游完整字体的存放原则

完整的 I.MingCP、EB Garamond 和 Noto Serif CJK 源字体体积较大，设计上不提交到仓库。

仓库保存：

• 生成后的 WOFF2 字体子集；
• 字体许可证；
• 字体来源和版本说明；
• 上游字体 SHA-256；
• 子集文件 SHA-256；
• 字体清单和缓存版本引用。

新机器、临时目录被清理或缓存不存在时，需要重新下载上游字体。如果临时目录中的字体仍然存在，可以复用，但 build-fonts.py 必须重新验证其 SHA-256。

上游 TTF、OTF、Python 虚拟环境和下载缓存都不得出现在 git status 中。

除非作者明确决定升级字体，并同步更新所有来源说明和生成结果，否则不得允许与固定哈希不同的上游字体。

如果下载文件的哈希不匹配，应停止并调查：

• 下载是否不完整；
• URL 是否被改动；
• 上游文件是否变化；
• 是否下载到 HTML 错误页；
• 是否使用了错误版本；
• 本地缓存是否损坏。

不能把不匹配的文件用于正式生成。

12. 字体重建命令

三个固定上游字体准备完成后，从仓库根目录运行：

"$FONT_WORK/venv/bin/python" scripts/build-fonts.py --iming "$FONT_WORK/I.MingCP-8.10.ttf" --garamond "$FONT_WORK/EBGaramond-wght.ttf" --noto-serif-cjk "$FONT_WORK/NotoSerifCJKsc-Light.otf"

脚本应完成：

• 验证三个上游字体的 SHA-256；
• 收集全部文字来源中的 CJK 码位；
• 确认上游字体包含所有所需字形；
• 在临时暂存目录中生成字体；
• 生成 WOFF2 子集；
• 按许可证设置派生字体名称；
• 计算字体大小和 SHA-256；
• 更新 scripts/font-subset-manifest.json；
• 更新 style.css 和 typography.js 中的缓存版本参数；
• 在完成引用检查后替换正式生成文件。

13. 字体方案与发布模式

iming-garamond 是默认排版方案：

• 拉丁文字使用由 EB Garamond 派生的 Daodao Garamond；
• 中文文字使用由 I.MingCP 派生的 Daodao Ming。

noto-system 是备用排版方案：

• 拉丁文字使用仓库已有的 Noto Serif；
• Apple 平台中文优先使用系统 Songti SC；
• 没有 Songti SC 或需要备用字体时，使用自托管的 Daodao Noto Serif SC 子集。

redacted 和 raw 是发布内容模式；iming-garamond 和 noto-system 是排版字体方案。这两组概念不能混淆。

14. 重建后允许出现的变化

根据新增字符类型，可能变化：

assets/fonts/daodao-ming-regular.woff2
assets/fonts/daodao-noto-serif-sc-light.woff2
assets/fonts/daodao-garamond-roman.woff2
scripts/font-subset-manifest.json
style.css
typography.js
FONT_KNOWN_LIMITATIONS.md（仅在字符数或已知限制说明需要同步时）

只新增中文字符时，通常是两个中文子集、清单及相应缓存哈希变化。Daodao Garamond 通常不会发生实质变化，因为它使用固定拉丁范围；生成脚本仍会重建并比较它。

如果出现其他仓库文件变化，必须逐项调查。

不得提交：

• 完整上游 TTF 或 OTF；
• Python 虚拟环境；
• 下载缓存；
• 临时站点目录；
• 构建日志；
• 与本轮无关的正文或脚本改动。

15. 字体清单和实际字形检查

检查 scripts/font-subset-manifest.json：

• JSON 可以解析；
• version 为 2；
• textSources 与 build-fonts.py 中的 TEXT_SOURCES 一致；
• cjkCodepoints 包含本轮新增的有效 CJK 码位；
• cjkCodepoints 无重复且保持排序；
• ming、garamond 和 notoSerifCjk 三项存在；
• 字体路径正确；
• bytes 与实际大小一致；
• sha256 与实际文件一致；
• sourceSha256 与三个固定上游字体一致；
• 两个中文字体的 glyphCodepoints 与实际结果一致；
• style.css 和 typography.js 的版本参数与字体 SHA-256 前十二位一致。

还必须使用 FontTools 逐一验证三份固定上游字体和三份生成字体：

• 三份上游字体的内部名称、字重和版本分别对应 I.MingCP 8.10、EB Garamond 1.003 和 Noto Serif CJK SC 2.003 Light；
• 三份生成的 WOFF2 均可完整打开、解压并解析字体表；
• Daodao Ming 的 family、subfamily、full name 和 PostScript name 分别为 Daodao Ming、Regular、Daodao Ming Regular 和 DaodaoMing-Regular；
• Daodao Garamond 的 family、subfamily、full name 和 PostScript name 分别为 Daodao Garamond、Regular、Daodao Garamond Regular 和 DaodaoGaramond-Regular；
• Daodao Noto Serif SC 的 family、subfamily、full name 和 PostScript name 分别为 Daodao Noto Serif SC、Light、Daodao Noto Serif SC Light 和 DaodaoNotoSerifSC-Light；
• Daodao Garamond 的实际 Unicode cmap 必须与固定 EB Garamond 源字体在 build-fonts.py 所定义 LATIN_RANGES 内的码位集合完全相等；
• Daodao Garamond 必须保留可变字体的 fvar 表及其字重轴。

不能只看到新码位出现在 JSON 中就认为完成。必须读取下列两个 WOFF2 的 Unicode cmap：

assets/fonts/daodao-ming-regular.woff2
assets/fonts/daodao-noto-serif-sc-light.woff2

必须独立重新计算当前全部文字来源和基础标点所需的完整 CJK 码位集合，并确认两个中文字体的实际 Unicode cmap 都与该集合完全相等：既不能遗漏任何所需码位，也不能包含任何多余码位。

16. 可重复性检查

每次正式重建都必须至少连续执行两次，并比较以下全部产物是否逐字节一致：

• 三份生成字体；
• scripts/font-subset-manifest.json；
• style.css；
• typography.js。

结果不一致时不得直接提交，应调查时间戳、工具版本、源文件、生成顺序或其他非确定性来源。

17. 重建后的双模式站点验证

必须再次构建：

node scripts/build-site.mjs --mode redacted --output "$FONT_WORK/site-redacted"
node scripts/build-site.mjs --mode raw --output "$FONT_WORK/site-raw"

确认：

• 两个构建均成功；
• 不再出现 stale-subset 错误；
• 字体清单结构正确；
• 字体大小和 SHA-256 与清单一致；
• style.css 的字体引用存在；
• typography.js 的预加载引用存在；
• 每个预加载字体都有相应的 font-face；
• raw/daodao.txt 与 daodao.master.txt 字节级一致；
• redacted 版本实际执行替换；
• redacted 版本不残留 redactions.json 中的 from 字符串；
• 输出全部位于仓库外；
• 构建没有产生新的意外仓库改动。

原始版本可以使用以下命令核对：

cmp daodao.master.txt "$FONT_WORK/site-raw/daodao.txt"

18. 视觉检查

普通常用汉字且全部自动检查通过时，视觉检查可以作为补充。

出现以下情况时应进行视觉检查：

• 新增生僻字；
• 新增 CJK 扩展区字符；
• 新增特殊中文标点；
• 字形容易与其他字符混淆；
• 字体文件变化范围异常；
• CSS、font-face、预加载或排版选择逻辑同时变化；
• 自动检查通过，但浏览器仍可能发生字体回退。

分别检查：

http://localhost:8000/?typography=iming-garamond
http://localhost:8000/?typography=noto-system

确认：

• 新字符不是方框、空白或替换字符；
• 没有明显回退为不协调的字体；
• 中文标点位置正常；
• 字重、行高和相邻文字协调；
• 切换方案后页面正常；
• 浏览器控制台没有与字体或页面加载有关的错误。

在 Apple 平台上，noto-system 通常优先使用本地 Songti SC。此时页面正常不能单独证明自托管 Daodao Noto Serif SC 的视觉效果。

Daodao Noto Serif SC 至少必须通过文件哈希、清单、Unicode cmap 和站点构建验证。如果必须视觉确认备用字体，应在没有 Songti SC 的环境中测试，或用开发工具临时强制选择该字体；不得为视觉测试修改并提交正式 CSS。

19. 已知字体限制

FONT_KNOWN_LIMITATIONS.md 是当前字体覆盖瑕疵及补救方案的专门记录。

每次字体重建后应确认：

• 已知限制没有被误写成“已经解决”；
• 新字符没有扩大现有限制；
• 字符数量和哈希说明与实际产物一致；
• 如出现新的回退、缺字或字形不协调，已经补充记录；
• 当前已知的备用方案拉丁字符回退与本轮 CJK 子集是否完整是两件不同的事情，不得混淆。

20. 重建后的完整 Git 检查

字符集重建会产生真实待提交变化，因此完成后必须重新执行第二章的整套 Git 审核。

确认：

• 所有字体、清单和缓存变化均由本轮重建产生；
• 没有意外修改正文；
• 没有完整源字体或临时文件进入仓库；
• 没有权限变化、重命名、符号链接或异常属性变化；
• 没有遗漏暂存、未暂存或未跟踪文件。

如果重建后作者又修改正文，必须再次运行站点构建；必要时再次重建。

21. 发布流程关系

当前 GitHub Actions 使用 Node.js 24。推送 main 后，发布流程分别构建脱敏 public 版本和受保护 raw 版本，并确认 raw/daodao.txt 与 daodao.master.txt 一致。

如果字体子集过期、字体哈希不匹配或缓存引用错误，发布应在更新线上版本之前失败。

本地提交前仍必须完成字符集检查，不能把 GitHub Actions 当作第一次检查。

22. 字符集结论用语

现有字符集无需更新时：

已执行 raw 和 redacted 双模式站点构建。现有 CJK 字体子集完整覆盖当前脚本所检查的正文、脱敏规则和界面文字；字体文件、清单及缓存引用验证正常，不需要重建字符集。

字符集已经重建时：

字符集已使用固定上游字体和固定工具版本重建。Daodao Ming 和 Daodao Noto Serif SC 的实际 Unicode cmap 与完整所需 CJK 集合完全相等，没有遗漏或多余码位；三份生成字体的内部名称、字体结构、Garamond 拉丁覆盖和可变字体表均正确；两次独立重建逐字节一致；上游哈希、生成字体哈希、字体清单、缓存引用以及 raw 和 redacted 双模式构建均验证通过。

字符集过期但未获准重建时：

当前文字检查已完成，但字体子集缺少指定 CJK 码位。普通审核保持只读；完成字符集重建并通过全部验证后才可以提交。

23. 可以提交的字符集条件

只有同时满足以下条件，才能说“字符集检查正常，可以提交”：

• 当前磁盘正文、脱敏规则和界面文字已保存；
• 当前 HEAD 已重新确认；
• raw 和 redacted 两种模式构建成功；
• 两个中文字体的实际 Unicode cmap 与独立计算出的完整所需 CJK 集合完全相等，没有遗漏或多余码位；
• 字体文件、清单及缓存引用一致；
• 三份生成 WOFF2 均可完整解析，内部名称正确，Daodao Garamond 的拉丁覆盖和 fvar 表验证通过；
• raw 输出与 daodao.master.txt 字节级一致；
• redacted 输出没有残留脱敏源字符串；
• 如进行重建，使用固定上游字体和固定工具依赖；
• 如进行重建，至少两次正式重建的全部产物逐字节一致；
• 重建后所有生成文件变化均已审核；
• 仓库中没有上游完整字体、虚拟环境或临时输出；
• 重建后没有再次加入未经检查的新字符。


十五、文件级技术检查

每轮检查：

1. JSON 是否正常解析；
2. 是否有重复或冲突的脱敏规则；
3. 文本是否为有效 UTF-8；
4. 是否意外增加 UTF-8 BOM；
5. 是否混入 CRLF 与 LF；
6. 是否有异常控制字符；
7. 是否有零宽字符、不换行空格、Unicode 行分隔符或乱码；
8. 是否出现 Unicode 替换字符 U+FFFD；
9. 是否存在 Git 冲突标记；
10. 是否有尾随空格或制表符；
11. 文件末尾换行是否正确；
12. 是否无意修改权限；
13. 是否无意修改文件名、大小写或扩展名；
14. 是否出现符号链接、子模块或异常二进制变化；
15. 已暂存、未暂存和未跟踪内容是否全部覆盖；
16. 数学乘号是否错误写成 x、X、ｘ或Ｘ。

同时：

• 搜索 Git 冲突标记；
• 解析和验证 redactions.json；
• 检查日期顺序、有效性和重复日期；
• 检查引号、括号和书名号的数量及嵌套；
• 检查文件末尾实际换行数量；
• 全量检查“惊喜礼品”专题编号；
• 执行 raw 和 redacted 双模式站点构建；
• 必要时记录 git hash-object daodao.master.txt，用于连续复查。


十六、推荐的每轮执行顺序

1. 重新确认 HEAD、分支和工作区状态。
2. 列出暂存、未暂存、未跟踪及属性变化。
3. 查看相对 HEAD 的统计、完整 diff、word diff 和字符级差异。
4. 确认旧内容是否完整保留。
5. 逐字校对新增和修改文字，并阅读上下文。
6. 检查中西文空格、标点、乘号 × 和特殊 Unicode 字符。
7. 检查日期、段落、相对时间和全文结构。
8. 全量核对“惊喜礼品”连续编号和名称变体。
9. 检查脱敏规则、实际替换效果和隐私风险。
10. 按需核实事实和逻辑。
11. 在仓库外运行 raw 和 redacted 双模式构建。
12. 如构建报告字符集过期，按权限边界处理重建。
13. 如已重建，检查来源、哈希、cmap、清单、缓存、可重复性和视觉效果。
14. 运行 UTF-8、BOM、CRLF、空白、控制字符、冲突标记和末尾换行检查。
15. 再次确认 HEAD、文件 blob、git status 和 git diff HEAD --check 没有在检查过程中变化。
16. 按第十七章格式先给结论，再报告证据和提交条件。


十七、最终报告格式

最终回答必须先给结论，不要先罗列检查过程。

建议顺序：

1. 是否存在误删或误改旧内容；
2. 当前改动统计和涉及文件；
3. 必须修正的明确问题；
4. 疑似问题或需要作者确认的事项；
5. 可选措辞建议，仅在作者需要润色时提供；
6. 脱敏和隐私结果；
7. “惊喜礼品”全量编号结果；
8. 乘号 × 专项检查结果；
9. 字符集与 raw/redacted 构建结果；
10. 日期、JSON、空白、乱码、冲突标记等技术结果；
11. 最终提交结论。

最终提交结论必须明确属于以下一种：

• 可以提交；
• 修正指定问题后可以提交；
• 仅在确认某个有意表达、昵称、事实不确定性或隐私风险后可以提交；
• 字符集仍需重建和复核，暂不可提交。

报告要求：

• 引用准确文件名和当前工作区行号；
• 删除内容标明旧行或 diff hunk；
• 引用足够短的原文帮助定位；
• 不要笼统地说“某一段有问题”；
• 不要把可选润色混入必须修正项；
• 不要因为发现一个问题就停止检查后续内容；
• 如有明确错误，不要含糊地说“总体没问题”；
• 只有可选建议时，不应阻止提交；
• 明确说明检查过程中是否修改了文件；
• 如果执行了作者明确要求的字符集重建，应列出由此产生的文件变化；
• 如果审查保持只读，应明确写“检查过程中没有修改任何文件”。

没有发现问题时，应明确写：

没有发现原有实质内容被误删或误改；当前改动为纯新增／已核对的有意替换。新增内容、脱敏规则、连续编号、乘号、字符集、日期和文件格式检查正常，可以提交。

作者所说的修改尚未保存时，应写：

当前磁盘文件及待提交差异与上一轮相同，没有检测到新的已保存修改。请先保存文件，再进行复查。
